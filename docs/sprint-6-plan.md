# Sprint 6 — детальный план (усиление после v1)

Источник: `docs/PLAN.md` этап 6.

**Scope:** только бюджет, пока явно не решим взять договоры / обязательства.

**Не начинать**, пока Sprint 4 зелёный на реальных данных и Sprint 5 закрыл запуск с нуля.

Это не часть v1. Набор работ можно резать: не обязательно делать всё за один спринт.

## 1) Цель спринта

Снять трение эксплуатации и добавить каналы, которые не нужны, чтобы доказать RAG.

К концу спринта (если брать полный scope) должно быть:

- загрузка Excel оператором по HTTP (не только CLI);
- клиент чата сверх CLI (`POST /chat` уже есть) — веб или Telegram;
- по необходимости: CSV, сверка реестра обязательств со статьёй, топ контрагентов.

## 2) Входные условия

- v1 в compose, ingest CLI, MCP, ассистент, золотой набор.
- Понятно, чего не хватает оператору в ежедневной работе.

## 3) Границы Sprint 6

### Входит в Sprint 6 (бэклог на выбор)

- HTTP-загрузка + статус ingest (принятые / rejects / warning по остатку).
- Тонкий веб-чат или Telegram как клиент к `POST /chat`.
- CSV тем же каноном и YAML-маппингом.
- Агрегат «топ контрагентов» / сверка `sum(obligations)` vs `obligation_amount` статьи
  (отдельный tool, цифры статьи по-прежнему из бюджета).
- Аудит запросов (кто что спросил), если появится вторая роль.

### Не входит в Sprint 6

- PostgreSQL «на всякий случай»;
- граф связей;
- fine-tune;
- банк-клиент и платежи;
- публичный интернет без отдельного решения по безопасности.

## 4) Sprint backlog (детализация задач)

Брать по приоритету оператора, не всё сразу.

## A. HTTP ingest

- `POST /ingest` (multipart) или класть файл в incoming + job.
- Ответ/статус: counts, путь к rejects, список warning по `remain_free`.
- Auth на запись (минимальный токен), чат по-прежнему read-only.

## B. Клиент чата

- Веб: одно поле ввода, ответ, sources.
- Или Telegram: тот же `POST /chat`.
- Не дублировать оркестратор.

## C. Форматы и сверка

- CSV → те же модели, что xlsx.
- Tool или отчёт: расхождение суммы обязательств реестра и статьи.
- Не затирать цифры бюджета.

## D. Наблюдаемость

- Журнал вопросов (без лишних ПДн в логах).
- Алерты: ingest warning rate, MCP 5xx.

## 5) Разбивка по дням (ориентир на 10 рабочих дней)

Имеет смысл, только если выбран узкий scope (например, только HTTP ingest + веб-чат).

### Дни 1–2

- Приоритеты с оператором: что болит после v1.
- Контракт HTTP ingest.

### Дни 3–5

- Загрузка файла + статус + тот же пайплайн Sprint 2.

### Дни 6–8

- Клиент чата **или** сверка/CSV — одно из двух.

### Дни 9–10

- Тесты, README, демо выбранного куска.

## 6) Definition of Done (DoD)

DoD зависит от выбранного scope. Минимальный осмысленный закрывающий набор:

- оператор обновляет индекс без SSH/CLI (если брали HTTP ingest);
- **или** пользователь задаёт вопрос не из CLI (если брали клиент);
- цифры бюджета по-прежнему из Excel, сверка не подменяет статью;
- v1-сценарии золотого набора не сломаны.

## 7) Демо-сценарий (пример: ingest HTTP + веб)

1. Открыть форму загрузки, отправить xlsx.
2. Увидеть отчёт (warning по остатку, если есть).
3. Задать вопрос в веб-чате по новой статье / договору.
4. Показать, что CLI-золотой набор всё ещё зелёный.

## 8) Риски Sprint 6 и меры

- Риск: расползание scope.
  - Мера: один канал (загрузка **или** чат-клиент) за спринт.

- Риск: HTTP ingest из чата.
  - Мера: разные эндпоинты и права; ассистент не вызывает загрузку.

- Риск: сверка путает оператора («какая цифра правильная»).
  - Мера: в UI явно: «официально — статья, реестр — справочно».

# Архитектура

## Задача

Дать быстрый поиск и ответы по годовому бюджету, договорам
и обязательствам (договоры, прошедшие бюджетный контроль).
Источник правды на старте — Excel. Интерфейс — чат с ИИ (RAG).
Платежи и кассовое исполнение в контуре нет.

RAG здесь обязателен: модель не «знает» договоры, она должна каждый раз
доставать релевантные записи из индекса и отвечать только по ним.

## Принципы

1. **Гибридный поиск.** Номер договора, ИНН, сумма и дата — это фильтры, не семантика.
   Свободный текст («обязательства по охране») — векторный поиск. Оба режима нужны сразу.
2. **Метаданные важнее чанков.** Одна строка Excel — это сущность с полями, а не кусок текста.
   Текст эмбеддим для поиска, поля кладём в payload Qdrant для фильтров и агрегаций.
3. **Разделение ответственности по языкам.**
   - Python: парсинг Excel, нормализация, эмбеддинги, пайплайн индексации, оркестрация RAG.
   - Go: MCP-сервер, HTTP API, строгая валидация запросов, стабильный runtime.
4. **Идемпотентная индексация.** Повторная загрузка того же файла не плодит дубли.
   Идентификатор точки = стабильный ключ сущности (`source_file + sheet + row` или бизнес-ключ).
5. **Ответ только по найденному.** Если индекс пуст или ничего не нашлось — ассистент говорит об этом,
   а не выдумывает суммы и договоры.

## Высокоуровневая схема

```
Excel (бюджет / договоры / обязательства)
        │
        ▼
┌───────────────────────────┐
│  ingest (Python)          │
│  parse → normalize →      │
│  embed → upsert Qdrant    │
└─────────────┬─────────────┘
              │
              ▼
┌───────────────────────────┐
│  Qdrant                   │
│  collections + payload    │
└─────────────┬─────────────┘
              │
              ▼
┌───────────────────────────┐
│  MCP server (Go)          │
│  search / get / aggregate │
└─────────────┬─────────────┘
              │
              ▼
┌───────────────────────────┐
│  assistant (Python)       │
│  LLM + tool calling + RAG │
└─────────────┬─────────────┘
              │
              ▼
     чат (CLI / HTTP / мессенджер)
```

Qdrant — единственное поисковое хранилище на первом этапе.
Реляционную БД не вводим, пока не появятся обновления из нескольких систем
или тяжёлые JOIN-отчёты, которые векторный индекс закрывает плохо.

## Компоненты

### 1. `ingest` — Python

Пакетная загрузка Excel в Qdrant.

- Чтение `.xlsx` через `openpyxl` / `pandas`.
- Определение типа листа: бюджет, договоры, обязательства (по имени листа, заголовкам или манифесту).
- Нормализация колонок к канонической схеме (см. ниже).
- Валидация обязательных полей и сверка свободного остатка с `лимит − принятые`.
- Отчёт: ошибки по строкам и warning, если excel-остаток не сошёлся с формулой.
- Сборка текстового представления сущности для эмбеддинга.
- Получение вектора (OpenAI / совместимый embeddings API, модель фиксируется в конфиге).
- Upsert в соответствующую коллекцию Qdrant.

Запуск: CLI (`python -m ingest path/to/file.xlsx`) и позже HTTP-эндпоинт загрузки.

### 2. `qdrant` — векторное хранилище

Три коллекции с отдельными схемами payload:

| Коллекция | Что хранит | Типичный запрос |
|---|---|---|
| `budget_items` | листья годового бюджета: лимит, факт, принятые обязательства | «остаток по статье охрана» |
| `contracts` | договоры и допсоглашения | «договор с ООО Ромашка» |
| `obligations` | обязательства — договоры, прошедшие бюджетный контроль | «какие обязательства по договору 12» |

Каждая точка:

- `id` — стабильный UUID/хэш от бизнес-ключа;
- `vector` — эмбеддинг текстового представления;
- `payload` — структурированные поля + `text` + служебные (`source_file`, `sheet`, `row`, `indexed_at`).

Индексы payload в Qdrant: keyword для строк-идентификаторов, integer/float для сумм,
datetime для дат. Без них фильтры будут полным сканом.

### 3. `mcp-server` — Go

MCP-сервер — единственный способ, которым LLM трогает данные.

Почему Go:

- один бинарник, предсказуемый runtime;
- строгие типы для фильтров и ответов инструментов;
- удобно отдавать тот же набор методов и как MCP, и как обычный HTTP JSON API.

Транспорт на старте: stdio (для Cursor / Claude Desktop) и streamable HTTP
(для ассистента в Docker). Оба режима читают один и тот же слой `tools`.

Сервер **не считает эмбеддинги сам**, если запрос уже с вектором.
Для текстового семантического поиска дергает тот же embeddings-сервис, что и ingest
(маленький Python sidecar `embed-svc` или прямой вызов API). Это сознательный компромисс:
одна модель эмбеддингов на запись и на чтение.

### 4. `assistant` — Python

Чат-оркестратор:

- принимает вопрос пользователя;
- вызывает MCP-инструменты (search / get / aggregate);
- собирает контекст (цитаты + метаданные + источник);
- просит LLM сформулировать ответ;
- возвращает ответ + ссылки на строки/договоры.

Модель — через OpenAI-совместимый API (провайдер в конфиге).
Системный промпт запрещает отвечать цифрами, которых нет в tool-результатах.

### 5. Интерфейсы

Порядок подключения, не всё сразу:

1. CLI-чат для отладки RAG.
2. HTTP API (`POST /chat`) — чтобы повесить любую UI-оболочку.
3. По желанию: Telegram / веб-виджет. Это клиенты одного и того же API.

MCP при этом остаётся отдельным входом: тот же индекс можно спрашивать из Cursor.

## Каноническая модель данных

Колонки в Excel будут разными. Ingest мапит их в эти поля.
Неизвестные колонки уходят в `extra` (JSON) и в текстовое представление.

### `budget_items`

Бюджет — дерево до **пяти** уровней. В Qdrant дерево не храним.

**В индекс попадает только лист** — статья, на которую сажают лимит
и обязательство. Промежуточные строки Excel нужны ingest, чтобы собрать путь,
но отдельными точками не становятся.

Иначе один и тот же миллион всплывёт и у родителя, и у детей, а модель их сложит.

Период бюджета — **только год**. Месячной нарезки нет.

На статье два разных остатка и две разные суммы обязательств:

| Понятие | Поле | Смысл |
|---|---|---|
| Лимит | `limit_amount` | доведённый годовой лимит листа |
| Факт | `fact_amount` | уже **отражённые** обязательства |
| Обязательства | `obligation_amount` | принятые обязательства, в том числе ещё не исполненные |
| Свободный остаток | `remain_free` | `limit_amount - obligation_amount` — сколько ещё можно принять |
| Не исполнено | `remain_unexecuted` | `obligation_amount - fact_amount` — принято, но ещё не факт |

Факт не равен «оплачено». Это не касса. Это обязательства, которые уже отразили.

Цифры лимита / факта / принятых обязательств и **свободного остатка**
берём из файла бюджета. Реестр `obligations` их не пересчитывает и не затирает.
Сверка «сумма реестра vs статья» — отдельный вопрос, не ingest.

Свободный остаток в Excel уже посчитан (`лимит − принятые`). Ingest делает **оба** шага:

1. **Пишем в индекс значение из Excel.** Это источник правды для ответов.
2. **Считаем контрольное** `limit_amount - obligation_amount` и сверяем.

Расхождение больше копейки (`0.01`) — строка не молча «исправляется».
В индекс уходит excel-значение, в отчёт ingest — warning:
лист, строка, excel, computed, delta.
Пересчитать и затереть официальный остаток нельзя: в файле может быть
округление или ручная правка, которую мы не имеем права подменить.

Если колонки остатка в файле нет **и** в той же строке есть принятые —
пишем вычисленное `limit - obligation` и `remain_free_source = computed`.
Если принятых в файле тоже нет (текущая смета) — `remain_free` не считать:
иначе остаток станет равен всему плану и соврёт про контроль.

`remain_unexecuted` — то же правило, если колонка есть; если нет — только считаем
`obligation_amount - fact_amount`.

`budget_summary` и чат **не пересчитывают** остаток заново. Они читают то, что лежит
в точке (как правило, excel). Пересчёт — только контроль качества ingest.

Вопрос «остаток по охране» без указания блока — выборка листьев с одним
`match_key` (производственные + управленческие) и сумма полей выше (не `spent`).
«Управленческие на охрану» — тот же ключ плюс `expense_kind=management`.

| Поле | Тип | Назначение |
|---|---|---|
| `expense_kind` | keyword | `production` или `management`; на листе сметы два дерева |
| `article_code` | keyword | `{expense_kind}:{код листа}`, например `production:1.8.2` |
| `article_name` | text | название листа |
| `article_name_norm` | keyword | нормаль имени для склейки |
| `match_key` | keyword | ключ контроля: обычно нормаль имени; для «прочие» — с родителем |
| `article_level` | int | глубина листа, 1…5 (ветка может оборваться раньше 5) |
| `l1_code` … `l5_code` | keyword | код уровня с префиксом kind; пусто, если уровень выше листа |
| `l1_name` … `l5_name` | text | название уровня |
| `ancestor_codes` | keyword[] | все коды от корня до листа, для фильтра «всё под статьёй X» |
| `year` | int | год бюджета, например 2026 |
| `limit_amount` | float | годовой лимит листа |
| `fact_amount` | float | отражённые обязательства |
| `obligation_amount` | float | принятые обязательства |
| `remain_free` | float | свободный остаток из Excel; fallback — `limit - obligation` |
| `remain_free_source` | keyword | `excel` или `computed` |
| `remain_unexecuted` | float | из Excel, если колонка есть; иначе `obligation - fact` |
| `unit` | keyword | подразделение / ЦФО |
| `amount_unit` | keyword | единица сумм в точке, у сметы `thousand_rub` |
| `currency` | keyword | валюта, по умолчанию RUB |

Правила ingest для иерархии:

- строка-родитель без собственной суммы (или сумма = итог детей) — не точка, только контекст пути;
- строка без детей — лист, даже если это уровень 1;
- деньги на родителе, все потомки нули или пустые — индексируем родителя, заглушки не пишем;
- нулевой настоящий лист без детей — в индекс;
- договоры и обязательства ссылаются на **лист** через `budget_article` = `match_key`,
  не на сырой код колонок A–G (коды в блоках перезапускаются).

### `contracts`

| Поле | Тип | Назначение |
|---|---|---|
| `contract_number` | keyword | номер договора |
| `title` | text | предмет |
| `counterparty` | text | контрагент |
| `inn` | keyword | ИНН |
| `signed_at` | datetime | дата заключения |
| `starts_at` / `ends_at` | datetime | срок |
| `amount` | float | сумма договора |
| `currency` | keyword | валюта |
| `status` | keyword | действует / закрыт / расторгнут |
| `budget_article` | keyword | лист бюджета (`match_key`), не родитель и не сырой код A–G |

Прохождение бюджетного контроля смотрим по коллекции `obligations`,
а не по флагу на договоре. Нет обязательства — в индексе контроля нет.

### `obligations`

Обязательство — договор (или его часть), прошедший бюджетный контроль
и севший на лист бюджета. Это не платёжка и не заявка на оплату.

Один договор может дать несколько обязательств, если сумма разнесена по статьям.
Договор без прохождения контроля в эту коллекцию не попадает.

| Поле | Тип | Назначение |
|---|---|---|
| `obligation_id` | keyword | номер / ключ обязательства |
| `contract_number` | keyword | договор, прошедший контроль |
| `year` | int | год бюджета |
| `accepted_at` | datetime | дата принятия (прохождения контроля) |
| `reflected_at` | datetime | дата отражения как факт; пусто, если ещё не факт |
| `amount` | float | сумма обязательства |
| `currency` | keyword | валюта |
| `purpose` | text | предмет / назначение |
| `counterparty` | text | контрагент |
| `inn` | keyword | ИНН |
| `status` | keyword | `accepted` — принято, ещё может быть не исполнено; `reflected` — уже факт; `cancelled` — снято |
| `budget_article` | keyword | лист бюджета (`match_key`), на который село обязательство |

Связи на первом этапе — логические, через одинаковые ключи в payload
(`contract_number`, `budget_article`). Отдельная графовая модель не нужна.

## Текстовое представление для эмбеддинга

Пример для обязательства (склеивается детерминированно):

```
Тип: обязательство
Номер: 1042
Договор: 12/2025
Контрагент: ООО Ромашка
ИНН: 7701234567
Год: 2026
Дата принятия: 2026-03-12
Сумма: 150000 RUB
Назначение: охрана объекта
Статья: 2.1 Охрана
Статус: принято
```

Так семантический поиск находит запись и по «охрана», и по «ромашка 150 тысяч».

## Потоки

### Индексация

1. Пользователь кладёт Excel в `data/incoming/`.
2. `ingest` читает манифест колонок (YAML) или автодетект заголовков.
3. Строки валидируются. Битые уходят в `data/rejects/` с причиной.
   Расхождение остатка с формулой — warning, не reject: в индекс идёт значение Excel.
4. Для каждой валидной строки: текст → embedding → upsert.
5. Пишется отчёт: сколько принято / отклонено / обновлено / предупреждений по остатку.

### Вопрос пользователя

1. `assistant` получает текст.
2. LLM решает, какой tool вызвать (или несколько).
3. `mcp-server` делает hybrid query в Qdrant:
   - эмбеддинг вопроса;
   - фильтры из слотов (даты, суммы, номер, ИНН, статус);
   - `limit` небольшой (10–20), с score threshold.
4. Результаты возвращаются как JSON: поля + короткий `text` + `score` + источник.
5. LLM отвечает по этим JSON, в конце — перечень источников.

### Переиндексация

Повторный ingest того же файла: upsert по стабильному `id`.
Удаление источника: `delete` по фильтру `source_file`.

## Контракт MCP-инструментов (черновик)

Полный список и примеры — в [FUNCTIONALITY.md](FUNCTIONALITY.md). Слой один:

| Tool | Зачем |
|---|---|
| `search_records` | гибридный поиск по коллекциям |
| `get_contract` | карточка договора + связанные обязательства |
| `list_obligations` | обязательства с фильтрами |
| `budget_summary` | лимит / факт / принятые / остатки по статье и году |
| `ingest_status` | состояние индекса (для отладки) |

Go-сервер валидирует вход через JSON Schema, которую же отдаёт в MCP `tools/list`.

## Структура репозитория (целевая)

```
chat-bot/
  docs/                  # архитектура, функционал, план
  ingest/                # Python: парсер Excel, нормализация, upsert
  embed_svc/             # Python: тонкий HTTP для embeddings (опционально)
  mcp_server/            # Go: MCP + HTTP API к Qdrant
  assistant/             # Python: RAG-оркестратор, CLI-чат
  deploy/
    docker-compose.yml   # qdrant, ingest, mcp, assistant
  data/
    incoming/            # исходные xlsx (не в git)
    rejects/
    mappings/            # YAML-маппинг колонок Excel → канон
  configs/               # модели, пороги, имена коллекций
```

## Инфраструктура

`docker compose` поднимает:

- `qdrant` — порт 6333;
- `mcp-server` — MCP HTTP + внутренний API;
- `assistant` — чат API;
- `ingest` — job/CLI, не постоянно живущий сервис на старте.

Секреты (API-ключи LLM/embeddings) — только в `.env`, не в репозитории.

Конфиг (не секреты): имя модели эмбеддингов, размер вектора, имена коллекций,
порог score, лимиты выдачи.

## Безопасность и границы

- Данные бюджетные: по умолчанию сервис во внутренней сети, без публичного интернета.
- MCP и HTTP API слушают localhost / docker network.
- Ассистент не выполняет запись в Excel и не меняет договоры — только чтение индекса.
- Ingest — отдельная команда с доступом к файловой папке, не из чата пользователя.
- В ответы не кладём сырой payload целиком, если там появятся лишние персональные поля;
  на старте отдаём канонические поля.

## Что сознательно не делаем в v1

- Отдельный PostgreSQL / граф связей.
- Fine-tune модели на договорах.
- Полноценный UI-админка.
- Платежи, касса, банк-клиент.
- Онлайн-синхронизация с 1С.
- Мультиарендность и роли сложнее чем «кто имеет доступ к сервису».

Этого достаточно, чтобы проверить качество поиска на реальных Excel
и только потом наращивать контуры.

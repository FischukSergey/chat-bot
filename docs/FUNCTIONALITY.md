# Функционал

**Текущий scope.** Реализуем ответы по бюджету. Сценарии договоров и обязательств
в этом документе — целевые, их не закрываем в спринтах, пока нет выгрузок.

Ассистент отвечает на вопросы по годовому бюджету, договорам
и обязательствам (договоры с бюджетным контролем).
Данные приходят из Excel, живут в Qdrant, наружу отдаются через MCP.
Платежей в контуре нет.

## Роли

| Роль | Что может |
|---|---|
| Пользователь | Задаёт вопросы в чате, получает ответ со ссылкой на источник |
| Оператор данных | Кладёт Excel, запускает ingest, смотрит отчёт загрузки |
| Разработчик | Дергает MCP-инструменты напрямую, смотрит `ingest_status` |

Запись через чат запрещена. Чат только читает индекс.

## Пользовательские сценарии

### Поиск договора

- «Найди договор с ООО Ромашка»
- «Что за договор 12/2025?»
- «Какие договоры заканчиваются в этом квартале?»

Ответ: карточка (номер, предмет, контрагент, сумма, срок, статус)
и, если нужно, список обязательств, прошедших бюджетный контроль.

### Обязательства

- «Какие обязательства по договору 12/2025?»
- «Что принято по охране, но ещё не отражено как факт?»
- «Проходил ли договор с Ромашкой бюджетный контроль?»

Ответ: список обязательств и сумма, если пользователь просит итог.
Итог считается по найденным записям, не «из головы» модели.
«Не исполнено» ≠ «не оплачено»: это принятое, но ещё не факт.

### Бюджет

- «Какой свободный остаток по статье охрана?»
- «Лимит, факт и принятые обязательства по ЦФО ИТ»
- «Где принятые больше лимита?»

Ответ: статья, год, лимит, факт, принятые обязательства,
`remain_free` и `remain_unexecuted` — как лежат в индексе (из Excel).
Инструмент остаток заново не считает. Слово «остаток» без уточнения —
свободный (`remain_free`), не касса.

### Сквозные вопросы

- «На какую статью село обязательство по договору с Ромашкой?»
- «Какая часть обязательств по договору уже факт?»

Ассистент вызывает несколько tools и склеивает ответ.
Если связи нет (обязательство без `contract_number`) — явно пишет, что связать нельзя.

### Отказ и уточнение

- Ничего не найдено → «в индексе нет таких записей», без выдуманных цифр.
- Запрос двусмысленный («остаток по охране») → уточняет статью / год, если веток несколько.
- Путает факт и принятые — в ответе оба числа с подписями, не одно «исполнено».
- Суммы в разных валютах → не складывает молча, показывает разбивку.

## Поведение ассистента

1. Сначала инструменты, потом формулировка. Цифры только из tool-результатов.
2. В каждом ответе — источники: файл, лист, номер договора / обязательства / статьи.
3. Короткий ответ по делу. Таблица — если записей больше трёх.
4. Язык ответа — язык вопроса (обычно русский).
5. Не даёт юридических и бухгалтерских заключений («можно ли не платить»).
   Только факты из индекса.

## Функции ingest

| Функция | Описание |
|---|---|
| Загрузка Excel | Один или несколько `.xlsx` из `data/incoming/` |
| Маппинг колонок | YAML: «Кол. договор» → `contract_number` |
| Автодетект | Если манифеста нет — пытается узнать тип листа по заголовкам |
| Валидация | Пустой номер договора, нечисловая сумма, битая дата — в rejects |
| Сверка остатка | `remain_free` из Excel vs `лимит − принятые`; расхождение — warning, индекс не переписываем |
| Идемпотентный upsert | Повторная загрузка обновляет точку, не создаёт вторую |
| Удаление источника | Снять из индекса все точки файла |
| Отчёт | Принято / обновлено / отклонено / warning по остатку, путь к rejects |

Форматы на старте: `.xlsx`. CSV — позже, тем же каноном.

## MCP-инструменты

Это весь функционал, который видит LLM. Имена стабильные, поля — JSON Schema.
Контракт Sprint 3 (вход/выход, `Source`, деньги): [api-sprint-3.md](api-sprint-3.md).
Сейчас в коде три tools; `get_contract` / `list_obligations` — целевые, не реализуем.

### `search_records`

Гибридный поиск по одной или нескольким коллекциям.

Вход:

- `query` (string) — текст запроса;
- `collections` (array) — сейчас только `budget_items` (по умолчанию она же);
  `contracts` / `obligations` — ошибка валидации, пока нет коллекций;
- `filters` — опционально:
  - бюджет: `year`, `expense_kind` (`production` / `management`), `match_key`,
    `article_code`, `article_name`, `ancestor_code`;
  - `amount_min`, `amount_max` (по `limit_amount`);
  - целевые (позже): `contract_number`, `inn`, `counterparty`, `status`,
    `budget_article`, `date_from` / `date_to`;
- `limit` — 1…20, по умолчанию 8.

Выход: список хитов `{ collection, score, fields, source }`.

### `get_contract`

Карточка договора.

Вход: `contract_number` **или** `inn` + `counterparty`.

Выход: поля договора + краткий список обязательств
(номер, статья, сумма, статус, даты принятия / отражения)
+ суммы принятых и уже отражённых. Если договоров несколько — список, без угадывания.
Нет обязательства — договор бюджетный контроль не проходил (или его нет в реестре).

### `list_obligations`

Выборка обязательств без обязательного семантического запроса.

Вход: те же фильтры, что у search, плюс `contract_number`, `status`
(`accepted` / `reflected` / `cancelled`), `year`.

Выход: записи + `total_amount` по этой выборке (если валюта одна).

### `budget_summary`

Агрегат по листьям годового бюджета. Родительская статья — фильтр по `ancestor_codes`,
не отдельная точка. Суммы всегда снизу вверх.

Вход:

- `year`, `unit` — опционально (год один, но в индексе может лежать несколько лет);
- `article_code` / `article_name` / `match_key` — код, имя или ключ склейки **любого** уровня (1…5);
- `expense_kind` — опционально сузить до производственных или управленческих;
  без него одноимённые листья двух блоков суммируются по `match_key`;
- `group_by_level` — 1…5, опционально: разбить выбранную ветку по этому уровню.

Выход:

- `filter` — какая ветка и год запрошены;
- `total` — `{ limit, fact, obligation, remain_free, remain_unexecuted }` по листьям ветки;
- `rows` — либо сами листья, либо свёртка по `group_by_level`
  (`code`, `name`, `level`, те же суммы).

Если фильтр слишком широкий и строк много — топ-N + «уточните статью».
Родителя и детей в одном ответе как независимые статьи не смешиваем.
Цифры статьи — из бюджета, не сумма реестра обязательств.
`remain_free` в ответе — как в индексе, без пересчёта в MCP.
В смете v1 колонки остатка нет: не вычислять `limit` как свободный остаток.

### `ingest_status`

Служебный. Число точек по коллекциям, дата последней индексации,
имена `source_file`. Для отладки, не для бизнес-ответов.

## Правила поиска

- Семантика работает по полю `text` / вектору.
- Точные идентификаторы (`contract_number`, `inn`, `obligation_id`) — только filter,
  не рассчитываем, что эмбеддинг «угадает» номер.
- Score ниже порога (конфиг, стартово ~0.35–0.45 в зависимости от модели) отбрасываем.
- Dedup: один `id` один раз, даже если попал в несколько запросов за ход.

## Нефункциональные требования

| Требование | Ориентир v1 |
|---|---|
| Задержка ответа чата | < 8 с на типичный вопрос (1–2 tool call) |
| Задержка MCP search | < 500 мс без embedding, < 2 с с embedding |
| Объём индекса | десятки–сотни тысяч строк Excel без смены архитектуры |
| Повторяемость | один и тот же вопрос + тот же индекс → те же источники |
| Наблюдаемость | лог: вопрос, вызванные tools, число хитов, latency |

## Критерии качества ответа

Проверяем на золотом наборе вопросов (см. план, этап 4):

- факт (сумма, дата, номер) совпадает с Excel;
- если записи нет — отказ, а не галлюцинация;
- источник позволяет найти строку в исходном файле.

Качество эмбеддингов и маппинга колонок важнее выбора «более умной» LLM.

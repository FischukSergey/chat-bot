# План реализации

Идём от данных к чату: сначала стабильный индекс, потом MCP, потом RAG.
Каждый этап заканчивается проверяемым результатом, не «каркасом ради каркаса».

**Текущий scope.** Работаем только с бюджетом (смета → `budget_items`).
Договоры, обязательства, их модели, маппинги и tools — не делаем ни в одном
спринте, пока не появятся выгрузки и явное решение расширить scope.

## Этап 0. Каркас репозитория

**Цель.** Можно клонировать и поднять пустой контур.

- Каталоги `ingest/`, `mcp_server/`, `assistant/`, `deploy/`, `data/`, `configs/`.
- `docker compose` с Qdrant.
- `.env.example` (URL Qdrant, модель эмбеддингов, ключ LLM).
- Общий конфиг: имена коллекций, размер вектора, лимиты.

**Готово, когда:** `docker compose up` поднимает Qdrant, healthcheck зелёный.

## Этап 1. Схема данных и маппинг Excel

**Цель.** Понять реальные колонки, зафиксировать канон.

- Взять 1–3 настоящих файла (бюджет, реестр договоров, реестр обязательств).
- Описать листы и заголовки в `data/mappings/*.yaml`.
- Утвердить канонические поля из [ARCHITECTURE.md](ARCHITECTURE.md).
- Разобрать иерархию бюджета до 5 уровней: какие строки — родители (только путь),
  какие — листья (точки индекса). Итоги родителей в индекс не пишем.
- Решить, что делать с объединёнными ячейками, шапкой в 2 строки, итогами внизу листа.

**Готово, когда:** для каждого типа файла есть YAML-маппинг и список обязательных полей.
Без реальных Excel дальше не идём — синтетика потом разъедется с продом.

## Этап 2. Ingest (Python)

**Цель.** Excel → нормализованные записи → Qdrant.

- Парсер `.xlsx` с маппингом колонок.
- Валидация строк, rejects-отчёт.
- Сверка `remain_free` (Excel) с `limit - obligation`; warning при расхождении > 0.01,
  в Qdrant всё равно значение из Excel.
- Сборка `text` для эмбеддинга.
- Создание коллекций Qdrant (вектор + payload indexes).
- Upsert с стабильным `id`.
- CLI: `python3 -m ingest load <file>` и `python3 -m ingest delete-source <file>`.

**Готово, когда:** повторный load того же файла не меняет число точек.
Выборка по `contract_number` — когда появится реестр.

Закрыто 2026-09-18 (только бюджет): `budget_items` 172 точки,
повторный load не плодит дубли, родители не проиндексированы.

## Этап 3. MCP-сервер (Go)

**Цель.** LLM и люди ходят в индекс одинаковыми инструментами.

- Реализовать tools: `search_records`, `get_contract`, `list_obligations`,
  `budget_summary`, `ingest_status`.
- JSON Schema на вход/выход, жёсткая валидация.
- Hybrid query: filter + vector (вектор — через embeddings API / sidecar).
- Транспорт: stdio и HTTP.
- Структурированные логи: tool, latency, hits.

**Готово, когда:** ручной вызов `get_contract` и `list_obligations` по известному номеру
возвращает те же суммы, что в Excel.

## Этап 4. Ассистент RAG (Python)

**Цель.** Вопрос на естественном языке → ответ со источниками.

- Системный промпт: только факты из tools, язык пользователя, отказ если пусто.
- Tool calling к MCP.
- CLI-чат для отладки.
- `POST /chat` (вопрос → ответ + sources).
- Золотой набор 20–30 вопросов по реальным файлам (поиск, сумма, отказ, сквозной).

**Готово, когда:** на золотом наборе нет галлюцинированных сумм
и точные вопросы (номер договора, дата) попадают в правильную запись.

## Этап 5. Упаковка и эксплуатация

**Цель.** Повторяемый запуск у себя и на сервере.

- `docker compose` на весь контур: qdrant + mcp + assistant.
- Документация запуска и переиндексации в README.
- Ротация логов, диск Qdrant в volume.
- Простая проверка здоровья: `/health` у mcp и assistant.

**Готово, когда:** с нуля: compose up → ingest файла → вопрос в CLI → корректный ответ.

## Этап 6. Усиление (после v1)

Не начинать, пока этап 4 не зелёный на реальных данных.

- HTTP-загрузка Excel оператором (сейчас достаточно CLI).
- Веб-чат или Telegram как клиент к `POST /chat`.
- CSV и второй формат реестра.
- Более умные агрегаты (топ контрагентов, сверка реестра обязательств со статьёй).
- PostgreSQL — только если понадобятся сложные JOIN и история изменений.
- Роли и аудит запросов, если сервис выйдет за пределы узкой группы.

## Риски

| Риск | Что делаем |
|---|---|
| Шапка Excel нестабильна, колонки плывут | YAML-маппинг на файл/шаблон, не «угадывание» вечно |
| Номер договора пишут по-разному (`12/2025` vs `12-2025`) | Нормализация ключа при ingest + поиск по нормализованному полю |
| Эмбеддинги плохо ищут номера и ИНН | Номера только через filter, не через вектор |
| Модель путает факт, принятые и свободный остаток | В `budget_summary` всегда три суммы + два остатка с именами полей |
| Модель выдумывает суммы | Промпт + в ответе обязателен source; тест на отказ |
| Слишком широкие вопросы бьют по всему индексу | Лимиты, порог score, `budget_summary` просит уточнение |
| Смена модели эмбеддингов | Переиндексация всего корпуса, размер вектора в конфиге |

## Решения, которые нужно принять на этапе 1

1. Какие именно Excel и листы — источник правды.
2. Какой провайдер эмбеддингов и LLM (OpenAI-совместимый endpoint).
3. Нужен ли доступ из Cursor через stdio MCP сразу или только HTTP-чат.
4. Кто оператор загрузки файлов и как часто обновляют реестры.
5. Как в живом Excel называются колонки факта и принятых обязательств,
   и чем в реестре отличается статус «принято» от «отражено».

Пока это не зафиксировано, код ingest лучше не разветвлять «на все случаи».
